## Summary

Design mode is a third sidebar mode, next to Sessions and Tasks. It is for working out what a UI should look like before writing code, without running the project.

A **design** is a prototype made of plain HTML pages that use one design system (X64). The design screen puts an agent chat beside a **canvas** that shows the pages live at a chosen viewport. The user iterates in three ways:
- chatting with the agent
- pinning **comments** on elements and sending them to the chat
- changing elements directly in a **visual editor**: move, resize, restyle, insert components, edit text

Every agent turn and every burst of edits by hand is a **snapshot** that the user can go back to.

A design lives in one of three places:

- **Workspace design.** It has its own agent and no branch, and is stored under `~/.moonlet/design/`. It is for exploring before there is any work to do. **Build it** later starts a session with the design attached.
- **Session design.** It is made inside a session with `/moonlet-design`, and the session's own agent writes it. Its pages live in the session's worktree under `docs/design/<slug>/`, are committed on the session's branch, and ship in the same PR as the spec and the code they led to. The session gets a **Design** tab beside Changes, Files and Plan.
- **Project design.** This is a session design after its PR merged: it is found under `docs/design/` on the project's base branch. Design mode lists it read only, and it can be the start of a new design.

## User journey

### A workspace design

1. The user presses ⌃⌘D, or clicks the pen icon in the sidebar's mode switch. The sidebar lists the workspace's design systems and designs.
2. **New design** (⇧⌘N) asks for:
   - a name
   - a design system, with a line saying what it holds, such as "11 cards, 2 layouts, synced 3 days ago from moonlet"
   - a brief

   The design system is the one the sidebar shows, else the first, also when the workspace's design systems are listed only after New design opened (`lib/design.test.ts` picks the shown design system, else the first, also when the list comes after it opened).

   **Create design** (⌘↵) starts the design's agent with the brief, and the design screen opens. New design closed while its design is being made still makes it, but leaves the view and any dialog opened since as they are; a toast says "<name> was made", with **Open** (`lib/designStore.test.ts` shows the design and closes the dialog while it is still open, leaves the view and another dialog opened meanwhile as they are, and offers the design in a toast).
3. The agent reads the design system and writes `pages/index.html`. A bar says "Claude is changing the design". The canvas shows "Claude is writing index.html" until the file exists, then reloads on every change.
4. The user switches the viewport to Phone. In Comment mode (C) they click the nav, type "Collapse into a menu on phone" and press ⌘↵. The comment goes into the chat and stays on the canvas as pin 1.
5. In Edit mode (V) the user:
   - drags the Git section above General
   - sets the heading's size to `--text-lg`
   - rewords a label

   A chip says "3 edits by hand · go with your next message". The next message tells the agent what changed.
6. The user asks for two more variants of the Git section. The agent adds `git-a.html` and `git-b.html`. **Overview** shows the three pages side by side, each labelled ("rows", "cards", "compact").
7. History lists the snapshots. The user previews the one from before variant B, then goes back to the current state.
8. **Build it** opens the New session composer in the design system's first source project. The design is its source, its pages and styles are listed as attachments, and the prompt reads "Implement the Settings page design". Create copies the design into the new session as a session design, so the session has a Design tab and can go on to the spec and the PR as in journey B. The design's header then says "Building in moonlet · implement-settings-page".

### B session design: requirements, design, spec, code in one session

1. In a session, the user and the agent agree on requirements in the chat.
2. The user types `/moonlet-design Prototype the page from the agreed requirements`. The chat input's slash menu explains the three forms: `/moonlet-design` (here, in this session), `new` (a separate workspace design) and `sync`. It also names the design system it will use.
3. The agent runs `"$MOONLET_BIN" design new --here …`. moonlet creates `docs/design/settings-page/` in the worktree with a pinned copy of the design system's styles, copies the whole design system into the session's `.moonlet/` for the agent to read, and opens the session's **Design** tab. The agent writes the pages there.
4. Comments and edits by hand on the Design tab go into the same session chat, as in journey A.
5. "Write the spec from the design" makes the agent write `docs/specs/X66-settings-page.md`. The spec has a `Design:` line, and its criteria name the elements they describe (`index.html` m24). Rejected variants are listed with the reason. The chat offers **Implement it** and **Back to the design**.
6. The Changes panel groups the files as Design, Spec and Code. Comments and snapshots stay in `.moonlet/` and are not committed.
7. **Implement it.** The agent writes the code, runs the checks and opens the PR. The PR's Design tab shows each page of the design beside a screenshot of the built screen. The PR description names the spec and the design.
8. After the merge, Design mode lists the design under **In projects**.

### Storage

- [ ] A workspace design lives in `~/.moonlet/design/<workspace id>/designs/<slug>/`, with:
  - `design.toml`: the name, the design system's slug, the brief, the viewport last used, the created time, the session it was built in, and `[pages.<name>] label = "…"`
  - `pages/*.html`
  - `assets/`
  - `comments.json`
  - `history/`

  Its slug comes from its name as a design system's does, and a name already used in the workspace gets a ` 2`; it is made only on a design system the workspace has. What moonlet trusts, its agent's chat, is kept in `<workspace id>/.records/designs/<slug>.toml`, outside the agent's folders, so the agent cannot change it without the user approving the edit. The workspace lists its designs by name; one whose `design.toml` cannot be read still lists, with its error, beside the others, and so does one whose record cannot be read: with that error, not as a design with no agent. A workspace with no designs folder has no designs, but a designs folder that is there and cannot be read fails the listing with the reason, rather than listing none. Removing a design deletes its folder and its record.   An agent turn ends when the design's agent stops working, however it stops: done, stopped with Stop (idle) or failed (error); asking the user is still within the turn. The daemon watches `terminal.updated` from a terminal tagged as a design's agent, so a stopped or failed turn's writes, and the edits by hand saved during it, are kept as its Agent turn too, never later as Edits by hand (`moonletd/tests/daemon.rs` an_agent_turn_stopped_or_failed_takes_its_snapshot_too). Edits by hand are the editor's saves, `design.write_page`: the daemon waits 10 s after each, each save cancelling the wait before it, and takes the snapshot after the last, so the snapshot comes also when the app closes meanwhile (tests shorten the wait with the daemon's `MOONLET_DESIGN_QUIET_MS`). While the design's agent works the wait takes nothing, as its pages may be half written: edits by hand not kept yet when the agent starts working are kept at once as their own snapshot, and any saved during the turn go with the turn's snapshot, labelled Agent turn (`moonletd/tests/daemon.rs` edits_by_hand_are_kept_on_their_own_when_the_agent_starts_a_turn, edits_by_hand_saved_while_the_agent_works_go_with_its_turn). A save is during the turn when the agent works as it is saved, even if the daemon's watcher hears the agent start only after it, such as behind another design's snapshot: the start then keeps nothing on its own, and the edits waiting, those from before the save too, go with the turn (`moonletd/tests/daemon.rs` edits_by_hand_saved_once_the_agent_works_go_with_its_turn_though_its_start_is_heard_late). The agent can change the pages the moment a message reaches it, before the daemon hears that it works, so they are kept before `chat.send` gives it a message while it is not in a turn, under the locks of the design's pages and history (`moonletd/tests/daemon.rs` edits_by_hand_are_kept_before_the_message_reaches_the_agent); a message while it works or asks the user is within its turn, and they go with it (`moonletd/tests/daemon.rs` edits_by_hand_go_with_the_turn_when_a_message_comes_while_the_agent_asks). A turn started otherwise keeps them as the agent starts working, each snapshot taken in the order of the agent's events; only such a turn's first writes, made before that, could still go with them. None does on a design with edits waiting today: the agent's first message comes as the design is made, and a message queued during a turn reaches it once the turn's snapshot holds the edits. Removing a design cancels its wait, under the locks of its pages and history, and a snapshot or restore writes inside the design's folder, never making it again (`moonletd/tests/daemon.rs` a_design_removed_while_its_edits_by_hand_wait_for_quiet_does_not_come_back). Anything changed means a file of `pages/` or `assets/` whose SHA-256 is not the one the last snapshot recorded, or one added or removed; a design with no snapshot compares with no files. A snapshot is `history/<n>/`, its files as they were and `snapshot.json` with its number, time, type, summary and each file's SHA-256, written last, so one cut short is not listed. The folder's number is the snapshot's: a record naming another is damaged and not listed either (`design/history.rs` a_record_naming_another_number_than_its_folders_is_not_listed). Numbers follow the highest folder's and are never given again; the newest 50 are kept and older ones removed. A folder is a snapshot's only under its number's own name, `1` and never `01`, so no two folders are one snapshot and rotating one never removes another (`design/history.rs` a_snapshot_folder_is_one_only_under_its_numbers_own_name). After the last number there is (4294967295), a snapshot, or a restore, fails before writing anything rather than start again at 0 (`design/history.rs` a_snapshot_after_the_last_number_fails_rather_than_wrap_to_zero). Every read and write goes through the designs folder as a handle: a link in `pages/` or `assets/` is left out, a linked `assets/` or `history/` folder is never read or written through, and a restore replaces a page that is a link rather than writing through it. Hidden files are left out. The daemon takes one snapshot of a design at a time, and a snapshot, like a restore, takes the pages' lock first, then the history's, the order every holder of both takes them in, so no save falls in between: the wait for edits by hand reads and takes them only under these locks, and one that ends during a save waits for it and keeps what it wrote (`moonletd/tests/daemon.rs` a_snapshot_of_edits_by_hand_waits_for_a_save_in_progress). (`design/history.rs` a_snapshot_is_taken_only_when_pages_or_assets_changed_since_the_last, the_newest_50_snapshots_are_kept_and_a_number_is_never_given_again, a_snapshot_never_follows_a_link_into_or_out_of_the_design; `moonletd/tests/daemon.rs` an_agent_turn_that_changed_the_design_takes_a_snapshot, edits_by_hand_take_a_snapshot_once_they_stop_for_a_while)
- [ ] Each snapshot has a type and a summary:
  - **Agent turn**, such as "Wrote git-a.html and git-b.html · 3 pages"
  - **Edits by hand**, such as "Moved section m24, restyled h2 m25, text of m30"
  - **Restored snapshot <n>**, such as "From 09:58"

  An agent turn's summary is made from the files changed since the snapshot before: the pages written, the pages removed and how many assets changed, then how many pages the design has. Edits by hand say what each did, as the app tells the daemon with each save (`design.write_page`'s `edits`): `moved section m24`, `restyled h2 m25`, `text of m30`, `deleted p m30`, an undo as `undid …`; one edit once, at most five then how many more. From an app that said nothing it is made from the files, as an agent turn's. A restore's summary is the time of the snapshot it made current, in the app's local time. (`design/history.rs` an_agent_turn_says_which_pages_it_wrote_and_edits_by_hand_say_what_each_did; `lib/designEdits.test.ts` say what each did to which element, an undone one as undone: moved section m24, restyled h2 m25, text of m30; `lib/designEditor.test.ts` says what the edits it carries did, for the snapshot the daemon takes once they stop, an undo as undone)
- [ ] Picking a snapshot previews it read only, with the blue bar "Previewing the snapshot from <time>, <type>. Nothing changes until you restore it", **Back to current** and **Restore**. Restoring makes it the current design and records a Restored snapshot entry.

  The History tab says "Snapshots of pages/ and assets/. The last 50 are kept." and lists the snapshots newest first, each with its type, summary and time (`10:41` today, else `Oct 24, 18:30`), listed again as each is taken (`design.changed` naming `history/`, which loads no page). The one previewed has Restore and Back to current under it too (`lib/designHistory.test.ts` lists each snapshot with its type, summary and time, as design.history gives them, newest first, says a time of today as its hour, and one of an earlier day with its date, names the previewed snapshot's time and type for the blue bar; `lib/designStore.test.ts` are listed from the daemon, and again as each is taken, which loads no page; `e2e/specs/design-history.e2e.ts` lists the snapshots in the History tab from the toolbar's History button, newest first, and a new one as its turn ends). The preview shows the snapshot's pages, in its page tabs and Overview, framed without the bridge, so nothing on them can be picked, commented or edited, outlined in blue; the hint line says `<page>.html at <time> · read only`. The canvas is in View and its mode switch is hidden, as the History board shows it; the editor's keys, undo, a pick in Layers, the Inspector and the Palette do nothing (`lib/designCanvas.test.ts` keeps the canvas in View, read only: no Comment, Edit or pick in Layers, no editor key and no undo). The Comments rail is read only too, its buttons off and saying why (`lib/designComments.test.ts` is read only while a snapshot is previewed: no Send, Send all or Resolve, which would change the current design's comments). Its frame asks for `designs/<slug>@<n>/pages/<page>.html`, which `design.file` serves from `history/<n>/`: a folder as deep as the design's own, so the page's `../assets/` and `../../../systems/<system>/styles.css` resolve as they do for the design's pages (`design/history.rs` a_snapshots_files_are_served_at_its_designs_depth_so_its_links_resolve_as_the_pages_do; `lib/designView.test.ts` is served from its snapshot as deep as its design's pages, so its links resolve as theirs, on a host of its own, never with the bridge). That host is a snapshot's, its page's key, an `s`, then its folder's (`designs/<slug>@<n>`), on which the scheme serves only that snapshot's files and design systems' (its styles): a link in the snapshot's page that leads the frame to the current page, another snapshot or another design gets nothing there, so the preview never shows the current page under the blue bar (`design_scheme.rs` a_snapshots_host_serves_only_that_snapshots_files_and_design_systems; `lib/designView.test.ts` is on a snapshot's host, its page's key then s and its folder's, so the scheme serves the frame only that snapshot's files, never the current page). A page that names another host's full `moonlet-design://` address could still leave it: the frame is cross-origin, so the app cannot read where it went, and WebKit has no CSP for a frame's own navigation (`navigate-to` never shipped); design pages link relatively. Back to current, a restore, another design, or a listing without the snapshot (rotated out of the 50) shows the current pages again (`lib/designHistory.test.ts` previews the snapshot picked, and goes back to current on Back to current, a restore, or once it is no longer listed; `e2e/specs/design-history.e2e.ts` previews a snapshot read only under the blue bar, with no mode switch, and Back to current shows the current page). A page, and a design, is never named with an `@`, and the snapshot's path goes only down into its pages or assets, never through `..` (`design/history.rs` an_at_sign_names_no_page_or_design_and_a_snapshots_path_never_climbs_out; `lib/designPage.test.ts` is never named with an @, as the daemon takes none: designs/<slug>@<n>/ is a snapshot's folder).

  A restore waits for the agent, as edits by hand do: the daemon refuses it with `busy` while the design's agent works, checked under the locks of the design's pages and history, and the bar and the tab offer no Restore then. It reads the snapshot first, then keeps what is not kept yet, as Edits by hand (which may rotate the snapshot out of the newest 50), then writes the snapshot's files into `pages/` and `assets/` exactly, removes every other file there that is not hidden, and records a **Restored snapshot <n>** entry holding them (`design/history.rs` restoring_a_snapshot_writes_its_files_exactly_and_records_a_restored_entry, the_oldest_of_50_snapshots_is_restored_after_what_was_not_kept_is_kept; `moonletd/tests/daemon.rs` a_snapshot_is_restored_over_rpc_but_never_while_the_agent_works). The edits by hand it keeps are taken from their wait only once it is done: a restore that fails, of a snapshot rotated out or one not as it was kept, leaves them waiting as they were (`moonletd/tests/daemon.rs` a_failed_restore_leaves_the_edits_by_hand_waiting_to_be_kept). The app then forgets the design's changes for undo and its edits by hand not told yet, made on pages that are gone, as on a stale save, and reads its pages again, which load on the canvas (`lib/designEditor.test.ts` forgets the design's changes and its edits by hand not told yet, as the pages they were made on are gone, reads its pages again and loads them on the canvas; `e2e/specs/design-history.e2e.ts` restores a snapshot, which writes the page file on disk and adds a Restored snapshot entry). A page the editor has read, changed by the agent in the same `design.changed` as the snapshot its turn took, is read again as for any other writer's change (`lib/designEditor.test.ts` is read again when the agent's change comes with the snapshot its turn took, as for any other writer's).

### Build it (workspace designs)

- [ ] **Build it** opens the New session composer (X54) with:
  - the project: the design system's first source
  - the design as the composer's source chip ("Design · Settings page")
  - the branch: `<prefix>implement-<design slug>`
  - the prompt: `Implement the <design name> design`
  - a note: "The project is the design system's first source. The design keeps a link to the session it starts."
- [ ] The design arrives as X54 attachments that follow its text contract: each sends the text it shows, in the order shown, before the prompt. There is one attachment per page, in `design.toml` order with `index.html` first, then one for the styles. Each sends one line:
  - a page: `<design dir>/<slug>/pages/<page>.html · <design name>, <label>`
  - the styles: `<design dir>/<slug>/system/styles.css · <design system> styles`

  Unfolding a page's attachment shows its line and a thumbnail of the page. × leaves that page out of the copy and the message, but the styles cannot be left out. No HTML is pasted into the message, so the first message stays small whatever the design's size.
- [ ] Create starts the session with `session.create {…, design: {workspace, slug, pages}}`. Before the agent starts, the daemon copies the design into the new worktree as a session design: the pages kept, `assets/`, `system/` and `design.toml`, as X65's session-design storage says. So the paths the attachments name exist when the agent reads them. Its pages link the copy's pinned styles, `../system/styles.css`, in place of the live system's; `design.toml` keeps only the kept pages' labels. The copy keeps the workspace design's slug, so the attachments, built before Create, name `<design dir>/<slug>/` with that slug and the project's `[design] dir`: where the worktree has that folder already, from a design of the same slug on the base branch, it is refused, "<design dir>/<slug> is in the worktree already: rename the design before building it" (`invalid_params`). The design, its pages, the session's workspace (the design's, given or not) and the project's place in it are checked before any worktree is made, all `invalid_params`; a refusal of the copy itself removes the worktree and branch made for it, logging what it cannot remove, and leaves a worktree it adopted as it was (`design/session.rs` a_workspace_design_copied_into_a_session_keeps_the_pages_chosen_linked_to_its_pinned_styles_and_records_the_session, a_workspace_design_is_copied_into_a_session_under_its_own_slug_never_over_a_folder_the_worktree_has; `moonletd/tests/daemon.rs` session_create_with_a_design_copies_it_into_the_worktree_before_the_agent_starts, building_a_design_whose_slug_the_base_branch_has_makes_no_session_and_leaves_nothing).
- [ ] The design records the session, `session` in its `design.toml`, and `design.list` gives it `built_in: {session, project}` (`moonletd/tests/daemon.rs` session_create_with_a_design_copies_it_into_the_worktree_before_the_agent_starts). Its header shows "Building in <project> · <session>", and the Designs index shows "built in <session>". From there on the session design is the one that changes; the workspace design stays as it was.

## Protocol and RPCs

- `design.list {workspace}` → `[{slug, name, kind: "workspace" | "session" | "project", system, project?, session?, path, brief, viewport, pages, updated_at, open_comments, agent, agent_state, needs_you, error, built_in?, system_updated?}]`. `pages` is `[{name, label}]`, `index` first, then by name; `updated_at` the newest change of a page, else the creation; `open_comments` the pins of `comments.json` whose `state` is `open`; `agent` its agent's chat while it is still that design's, with its `agent_state` and `needs_you` as `design.systems` gives a sync agent's. Entry 7a lists workspace designs only; since entry 12a it also gives the session designs of the workspace's open sessions (`session`, `project`, their `path` in the worktree, the session's structured agent as `agent`, `system_updated` when true) and the project designs of the projects in its sections (`project`, `path` in the repository such as `docs/design/settings-page`, `updated_at` and `open_comments` 0, no agent), and a workspace design built in a session has `built_in: {session, project}`. (`moonletd/tests/daemon.rs` a_new_design_starts_its_agent_in_its_folder_on_its_design_system, a_session_design_is_made_in_its_worktree_and_reached_by_its_session_and_slug, a_project_design_on_the_base_branch_is_listed_and_copied_into_a_new_workspace_design, session_create_with_a_design_copies_it_into_the_worktree_before_the_agent_starts)
- `design.create {workspace, name, system, brief, session?, spawned_by?}` → the design, with `agent_error`. With `session` it is a session design in that session's worktree, which must be in `workspace`, and no agent of its own starts: its `agent` is the session's structured agent, as `design.list` gives it, and `agent_error` is `null`; no `design.open` is sent for `spawned_by` (`design new --here` sends its own); a session moonlet does not have is `invalid_params` (until entry 12 it failed with `not_yet`). Otherwise it is a workspace design, and its agent starts. A system the workspace does not have fails with `invalid_params`. (`moonletd/tests/daemon.rs` a_design_on_an_unknown_system_or_in_an_unknown_session_is_refused, a_session_design_is_made_in_its_worktree_and_reached_by_its_session_and_slug) When the agent's record cannot be saved or its first message cannot be sent, the design is still made, `agent` is `null` with `agent_error`, and the agent's chat is stopped and removed, as is a sync agent's on `design.system.create` (`moonletd/tests/daemon.rs` a_designs_agent_whose_record_cannot_be_saved_leaves_no_chat_behind, a_design_mode_agent_that_cannot_take_its_first_message_leaves_no_chat_behind).
- `session.create` (X54) gains `design?: {workspace, slug, pages}`. Before the agent starts, the daemon copies that workspace design into the new worktree as a session design and records the session on the workspace design. The design must be in the session's workspace; a page it does not have is `invalid_params`, and no session is made. Without `design`, `session.create` is unchanged. (`moonletd/tests/daemon.rs` session_create_with_a_design_copies_it_into_the_worktree_before_the_agent_starts)
- `design.copy {workspace, from: {project, path}, name}` copies a project design into a new workspace design → the design, with `agent_error`, as `design.create`. The project must be in the workspace; the design is read from its base branch's git objects. Its pages link the workspace's live design system again, and its assets, labels, viewport and brief are kept; the system must be the workspace's. Its agent starts, its first message saying it is a copy of `<path>` on `<base>` whose pages are written already, then the brief it had, so it never writes them anew. A design the branch does not have is `invalid_params`, and so is a `path` that is not a folder of the project's design folder, `<design dir>/<slug>` as the listing gives it, whatever the branch has there (`moonletd/tests/daemon.rs` a_project_design_on_the_base_branch_is_listed_and_copied_into_a_new_workspace_design, design_copy_takes_only_a_folder_of_the_projects_design_folder).

## Security considerations

- Pages are untrusted HTML and JavaScript written by an agent. The canvas iframe has `sandbox="allow-scripts"` and never `allow-same-origin`, so a page cannot reach the app, Tauri's IPC or another design.
- Every page is served with `Content-Security-Policy: default-src moonlet-design: data: blob: 'unsafe-inline'; connect-src 'none'; form-action 'none'; frame-src 'none'`. A prototype cannot fetch or post anywhere.
- The editor bridge (the comment bridge since entry 8) talks to the app only through `postMessage`. The app accepts only messages from the canvas frame's window, with a known message type, and checks every `data-mid` and page name it gets before it writes anything: a `data-mid` is `m` and digits, a tag a tag's name, a box four numbers, and text is cut to 60 characters; anything else is dropped (`lib/designBridge.test.ts` takes a pick with its element's data-mid, tag, text and box, cuts the text to 60 characters on one line, and drops a pick whose data-mid, tag or box is not one, takes the page's ids, the boxes of the pinned elements, and C and Esc, tells the page its mode, and the pinned elements once each, asks the page for its data-mids with a hello, once the app listens, drops a message of an unknown type, or that is not an object). The daemon checks a pin's page, `data-mid` and tag again before it writes `comments.json`. The bridge takes messages only from its parent, the app's window, so the page's own scripts cannot change its mode or ask for boxes (`lib/designBridge.test.ts` takes messages only from the app's window, never from the page's own scripts).
- The page's own scripts run in the same frame as the bridge and can post the same messages to the app: they could open a comment box on an element of their choosing, report other ids or boxes, or press C. That affects only the comments the user makes on that page, which the user still writes and sends; nothing is sent or saved without the user's Keep or Send, and the message the agent gets is built by the app from checked fields. They can also report the page's `data-mid`s without some that are there, which marks real pins orphaned: those pins leave the list and the canvas for **Orphaned**, and **Send all** leaves them out, until the page loads again or the user resolves them.
- A workspace design's agent and the sync agent (X64) get `--add-dir` folders they may only read. Their `--settings` deny `Edit(//<folder>/**)`, which covers every Claude Code file-editing tool. Bash is not covered by those rules, but in Accept edits mode every Bash command other than `"$MOONLET_BIN" design …` asks first, so the user sees any command that could write there.
- `design.write_page` writes only `pages/*.html` of the named design: a page name with a `/`, a `\` or a leading `.` is refused, and it writes through the designs folder as a handle, so a design or `pages` folder swapped for a link is never followed (`design/pages.rs` a_page_is_never_read_or_written_through_a_link_or_by_a_name_that_is_not_a_page). Each save is over a version, so a page's scripts, which could send the bridge's messages, can at most make an edit the user then sees on the canvas and can undo; they cannot write anything but the user's own page through the editor, as the app builds every saved text from the page's source and the checked `data-mid`, never from the live page. The app checks every message the bridge sends (a tree's ids, tags and depths, a text's length, a scroll's numbers, a key from a known set), and the bridge every message the app sends, taking them only from its parent: an edit names ids `m` and digits, a box id too, and a select only an id; an inserted element's source comes from the design's own pages. Forged keys from the page could delete or wrap the selected element as the user's keys would: the edit shows on the canvas, goes with the next message, and ⌘Z undoes it. For a session design it resolves inside the worktree's design folder and rejects any path that leaves it (`design/session.rs` a_session_design_is_found_in_its_worktree_but_never_through_a_link_or_outside_it).
- Inspector values go into the element's `style` attribute in the page's source. A property is lowercase letters and `-`; a value is letters, digits, spaces and `#%.,()/+*!_-`, balanced parentheses, at most 200 characters, never a quote, `;`, a brace, an angle bracket, a backslash, `url(` or `expression(`, so it can neither end its declaration or the attribute nor load anything, and never `/*` or `*/`, which would open or close a comment and hide the declarations after it, while a `/` alone stays, as in `grid-column: 1 / 3` or `font: 12px/1.5` (`lib/designEdits.test.ts` refuses a value that opens or closes a comment, which would hide the declarations after it, and keeps a slash where CSS has one); anything else is refused before the source is touched. Only what is new is checked: parts the property's value already had in the page's source (a background's `url()`) stay as written, and nothing new can come with them. The attribute is written in double quotes with `&` and `"` as entities, so even a value read from the agent's own style stays inside it (`lib/designEdits.test.ts` refuses a style value that could end the declaration or the attribute, or a property that is not one; `lib/designInspector.test.ts` shows a field's inline value, else what the page computes, and refuses a free value that could break out of the style). A drag, a handle or a forged message from the page's scripts gives only ids, a place (`above`, `below` or `into` an id) and `left`, `top`, `width` and `height` in whole or decimal px; the selection's computed style is only the Inspector's properties, each at most 200 characters, and is only shown (`lib/designBridge.test.ts` takes where a drag would drop and the move on drop, the size or place a handle or a drag gives in px, and a snippet's drop, takes the selection's computed style, only the Inspector's properties, and tells the page an off-system selection). Such messages can at most move, resize or place the user's elements as the user's own drag would, which shows on the canvas and ⌘Z undoes.
- An inserted snippet's HTML comes only from the design's own design system's cards: the daemon picks the system from the design's `design.toml` and reads its cards through the system's folder (`design.kit`); the page tells the app only where a drop lands, never what it inserts. Its markup is the card's, which runs in the same sandbox as the page.
- A project design is read from git objects (`git ls-tree` and `git cat-file blob`, its base branch never taken as an option), never checked out, and is rendered in the same sandbox.

## Out of scope

- Designs on remote hosts, and sharing designs between workspaces or people.
- Exporting to Figma or to Claude Design.
- Free drawing (vectors, pen tool) and image editing.
- Multi-select editing and alignment tools (a follow-up). Single selection plus copy and paste covers the first version.
- Agents other than Claude Code (ADR 0013).
- Using real components or real data: pages are static HTML with the design system's styles.
- Turning the off-system inline styles into classes. The user asks the agent for that.
- Comparing design and build pixel by pixel. The PR panel shows them side by side only.

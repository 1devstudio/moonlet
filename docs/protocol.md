# moonlet wire protocol

`moonletd` speaks one protocol to every client: the desktop app, the `moonlet` CLI, remote connections tunnelled through `ssh host moonletd proxy`, and the phone app (X39). The Rust source of truth is `crates/moonlet-proto`.

## Transport

- **Local:** Unix socket at `~/.moonlet/run/moonletd.sock`. The directory is `0700` and the socket is `0600`. The daemon also checks that the peer's uid matches its own.
- **Remote:** `ssh <host> ~/.moonlet/bin/moonletd proxy` bridges stdio to the remote daemon's socket and starts that daemon if it is not running. The daemon outlives the SSH connection.
- **Tailnet (X39, X57):** TCP port 47428 on the host's Tailscale addresses only, while tailnet access is on. Paired phones and Macs connect here. The first frame must be `auth`; see Messages.

## Framing

```
[u32 BE length of kind + payload][u8 kind][payload]
```

| kind | name | payload | direction |
|---|---|---|---|
| 1 | JSON | one `Message` (see below) | both |
| 2 | Output | `[u32 BE session id][raw PTY bytes]` | daemon to client |
| 3 | Input | `[u32 BE session id][raw bytes]` | client to daemon |
| 4 | Pack | `[u32 BE transfer id][git pack bytes]` | both, between a worker and its central host (X60) |
| 5 | RunOutput | `[u32 BE run id][u8 stream: 1 stdout, 2 stderr][bytes]` | daemon to the client that started the run, and a worker to its central host (X62) |

Frames are at most 16 MiB. A git pack goes as Pack frames of at most 1 MiB each, so it never holds up terminal output, and an empty one ends it. The JSON message that uses the pack follows its frames and names it by transfer id (`pack`). A `worker.ping` and its reply skip ahead of queued pack chunks (they go out before the next chunk), so a large pack on a slow link never makes the central host drop the worker. The daemon takes Pack frames only from a `moonletd-worker` connection; any other client that sends one is disconnected with an id-0 `forbidden` error. Either side ends the connection (id-0 `too_large` from the daemon) when one pack passes 1 GiB, the packs waiting on it pass 1 GiB together, or more than 16 are waiting. A whole pack no message takes within 60 s is dropped, and so is a pack in part whose next chunk does not come within 60 s; a chunk for a pack already whole ends the connection. The limits hold per connection, with no budget shared across connections: only paired workers may send packs, and each is one of the user's own machines. PTY bytes are never wrapped in JSON. The daemon coalesces output per client and flushes every 8 ms or at 64 KiB.

## Messages

Every JSON message is an object with a `t` tag:

- `hello` `{protocol, client}` is sent by the client first. The daemon answers `welcome` `{protocol, daemon_version, host, pid}`, or closes the connection if `protocol` differs from its own.
- `request` `{id, method, params}` gets exactly one `response` `{id, result | error}`. `error` is `{code, message}`.
- `event` `{name, data}` is a daemon broadcast to every connected client.
- On a worker's connection to its central host (hello `client` `moonletd-worker`, X41), requests also go the other way: the central host sends `request`, numbered from 1, and the worker answers with `response`. `id` 0 stays the reply that ends a link. No other client ever receives a request.
- `auth` `{token?, pair?, device?, kind?, route?}` comes first on a tailnet connection, before `hello` (X39). `kind` (`phone` or `desktop`, X57) says what is pairing; it defaults to `phone`, and it must be the kind the code was made for, or the pairing is refused. The daemon answers `authed` `{device_id, token?, protocol, daemon_version, host, os}` (`token` only after a pairing; `os` is `macos` or `linux`, X58; daemons before X57 leave out the last four) or one `response` with `id` 0 and error `unauthorized`, then closes. With `route`, everything after `authed` comes from `ssh <route> moonletd proxy`.

## Attach ordering

`session.attach` returns `{info, snapshot}`. `snapshot` is an escape-sequence stream that redraws scrollback, the screen, the cursor and terminal modes on a freshly reset terminal. The daemon takes the snapshot and subscribes the client under the same lock, so the first Output frame after the response continues exactly where the snapshot ends.

## Methods

Method names and parameter structs are in `crates/moonlet-proto/src/methods.rs`; result types are in `types.rs`. Groups:

- `daemon.*`: info (with `data_dir`, the daemon's data folder, X55), shutdown, upgrade.
- `terminal.*`: create, list, attach, detach, resize, kill, write, search.
- `agent.report`: state reports from agent hooks (`moonlet hook …`).
- `workspace.*`, `section.*`, `project.*` and `session.*`: workspaces, their sections, projects, worktree sessions, scripts (X32). Each project has an `identity {origin, root}`, its normalized origin without credentials and its root commit, and `project.identity {path}` returns that of any folder (X41). `session.archive` takes `delete_remote` and returns `{ remote_error }` (X55; older daemons return `true`).
- `profile.*`: Claude profiles, the config folders workspaces run Claude with (X33).
- `claude.*`: version (the installed Claude Code, and whether an update runs) and update (runs `claude update`) (X36). Events: `claude.update_output` per line while it runs, `claude.update_done` when it ends.
- `chat.*`: state, summaries (every chat's state without items, X40), send, send_now and unqueue (a queued message, X49), aside (a side question answered by a tool-less fork of the conversation, X49), permission, interrupt, settings (model, effort, permission mode) for structured agents (X6, X7). Events: `chat.item`, `chat.state`.
- `git.*` and `gh.*`: status, diffs, staging, commit, log, PRs, issues.
- `git.settings` and `git.set_settings`: the host's Git settings, kept in `~/.moonlet/git.toml` (X55). `git.unpushed` (uncommitted files, and commits on the session's `branch` or a detached HEAD that no other branch or remote has; `merged_head`, a merged PR's head commit, counts as on origin) and `git.push` (`push -u origin <branch>`, else HEAD) for the archive prompt. Event: `git.settings_changed`, the whole settings after a change.
- `repo.*`: adding a project from GitHub (X59). gh_status (gh installed, and the signed-in login), lookup (a repository's details, through gh or `git ls-remote`), list (the signed-in user's repositories, each marked when a project already has it as origin), clone_target (what is at the folder a clone would go to), clone (starts a clone under an id the app chooses and answers at once) and clone_cancel. Events: `repo.clone_progress` with git's step and counts, `repo.clone_done` with the new project, an error or `cancelled`.
- `fs.*`: list, files, read, write, watch.
- `shell.history`: the login shell's history for input suggestions.
- `mobile.*`: status, set_enabled, pair_start, pair_cancel, revoke, hosts, unpair for tailnet access (X39, X57). `mobile.pair_start {kind?}` makes a code that pairs only a device of that kind, `phone` by default: Settings › Phones asks for `phone`, Settings › Machines › Hosts and `moonletd pair` for `desktop`. It refuses `cloud`: a cloud machine pairs only with its join code. Only the desktop app may call them, except `mobile.hosts`, which phones use, and `mobile.unpair`, with which a paired device removes itself from its own connection. Events: `mobile.changed`, `mobile.paired`, `mobile.pair_ended`.
- `link.*` (X41, X61): get, set, retry and pair this machine's link to its central host, kept in `~/.moonlet/link.json`. `link.get` returns `{central: {name, addrs} | null, worker: {id, name, enabled, slots}, state}`, never the token; `state.kind` is `off`, `connecting`, `connected` (`since`), `reconnecting`, `needs_update` (`daemon_version`), `refused` (the central host no longer accepts this Mac) or `error` (`message`). A link in `needs_update`, `refused` or `error` tries again on `link.retry` or any `link.set`. `link.set {central?, worker?: {enabled?, name?, slots?}}` changes only what it is given; `slots` (X62, default 2) is how many routed commands this machine runs at once, from 1 to 64; `central: null` clears it. `link.pair {central: {name, addrs}, code}` (X61) pairs this machine with the central host using a pairing code from it, as a `desktop` device named after the worker, and stores the central host with the token it gets; it fails with `pair_failed` and changes nothing when the pairing does not work, with `conflict` and changes nothing when the central host was set while it ran, and with `pair_unsaved` when the central host paired this machine but the token could not be saved. `link.set`, `link.retry` and `link.pair` answer the Mac's app and a paired Mac over the tailnet, which may not give `link.set` a `central`; a phone and the CLI get `forbidden`. Event: `link.changed`, the same as `link.get`.
- `sync.*` (X60): live copies. On this Mac's daemon, `sync.start {session}` (a session on the central host), `sync.list`, `sync.retry {copy}`, `sync.resolve {copy, path, keep: "central" | "worker"}` and `sync.use_central_branch {copy}` (a diverged copy's branch moves to the central host's commit; this Mac's commits stay on `<branch>-this-mac`), each giving `Copy {id, host, session, path, state, setup, differs, too_big, diverged}`; `state.kind` is `copying`, `in_sync`, `syncing` (`files`), `waiting` or `paused` (`reason`). `setup` is `null` or `{state, command, approved}`, `state.kind` being `needs_approval`, `running`, `done`, `failed` (`exit`) or `skipped`, `command` the copy's setup command now and `approved` whether it was approved. `sync.run_setup {copy, command}` approves and runs the copy's setup, refused with `setup_changed` (message: the current command) when the command is no longer the copy's, and with `no_setup` when the copy has none; `sync.skip_setup {copy}` skips one waiting for approval. `sync.project_get {identity}` and `sync.project_set {identity, keep_new}` → `{keep_new}`: whether new sessions of that project on the central host get a copy here. `sync.project_set` fails with `no_central_host` when this Mac has none and `no_identity` for a project without a root commit. While a project keeps new sessions, the worker link stays open and the worker follows the central host's `sessions.changed` and `projects.changed`; a new session waits 3 s before it is kept, so the composer decides first. `sync.decline {session}` → `true`: that session gets no copy, the composer's unticked checkbox. `sync.run_setup`, `sync.skip_setup`, `sync.project_set` and `sync.decline` answer only the Mac's app: a paired device or the CLI gets `forbidden`. `sync.stop {copy}` removes the copy and returns `{folder, leftovers}`, the files it saved under `~/.moonlet/sync-leftovers/<copy folder>-<YYYYMMDD-HHMMSS>/`; it fails with `not_saved` when a file could not be saved and `failed` when the worktree could not be removed, and the copy then stays, paused. Event: `sync.changed`, the copy plus `newly_differing`, the paths that started to differ with this change, and `removed {reason: "stopped" | "archived", folder, leftovers}` when the copy went. Over the worker link, the worker asks `sync.open`, `sync.fetch` and `sync.offer {copy, base, tree, head, too_big, pack, resolve?}` → `{from, tree, base, head, differs, too_big, pack}` (only from a `moonletd-worker` connection, for its own copies), and `sync.close {copy}` when it stopped keeping one; the central host sends `sync.update` → `{applied, tree}` (`tree` is `null` when the worker was busy offering), and `sync.closing {copy, reason: "archived"}` → `{folder, leftovers}` once it has archived the session, without waiting for the answer. `sync.resolve` fails with `invalid_params`, `paused`, `not_ready`, `disconnected` or `busy` when it could not be done. An offer the central host turns away is made again after 300 ms, doubling up to 5 s. A `sync.update` with `off_branch` (the branch the session is on, empty for a detached `HEAD`) pauses the copy until one without it; a `sync.offer` while the session is off its branch fails with `wrong_branch`, whose message is that branch. Commits move the other side's branch only forward; `diverged {ahead, behind}` counts the commits only on this Mac and only on the central host. The central host reconciles: a worker takes an update only while its files are its base, and otherwise offers them. Their objects travel in Pack frames.
- `heavy.*` (X62): a project's heavy commands. `heavy.get {project}` → `{config, approved, error}`: the `[heavy]` table of the project's folder (`commands`, `os`, `env`, `outputs`), the approved `{commands, env}` or `null`, and why the table cannot be used, if it cannot. `heavy.set {project, heavy}` writes `[heavy]` in the project's `.moonlet/config.toml` and never approves. `heavy.approve {project, commands, env}` approves exactly those lists, together, kept in `~/.moonlet/heavy.json` by project identity; it fails with `changed` when either list differs from the config, `no_identity` for a project without a root commit and `invalid_config` when the table cannot be used, and answers the Mac's app and a paired Mac only: a phone and the CLI get `forbidden`.
- `exec.route {session, command, cwd, tool_use_id?}` (X62) → `{route, reason}`: whether an agent's Bash call may run on another machine. `reason` is `no_session`, `outside_worktree`, `invalid_config`, `not_heavy`, `not_approved`, `env_not_approved` or `claude_rule`. moonlet's `PreToolUse` hook asks it.
- `exec.run {session, argv, cwd, env, tool_use_id?}` (X62) → `{run, host}`: runs a heavy command for `moonlet exec`, after checking `argv` as `exec.route` would (refused with `not_routable` and the reason). Its output follows on the same connection as RunOutput frames, the first stderr line being `moonlet: running on <host>`, then the event `exec.exited {run, status}`, `status` being the exit status or 128 + N for signal N. Only the approved `env` names are passed on, with `MOONLET_ROUTED=1` and `MOONLET_SESSION`; stdin is `/dev/null`. `exec.cancel {run}` → `true`/`false` stops a run of the same connection: SIGTERM to its process group, SIGKILL 5 s later. A run whose connection goes away is stopped the same way.
- `exec.status` (X62) → `{host, running, skips, routed}`: this machine (`{name, os, cores, load, slots, used}`), the routed commands going on wherever they run (`{job, session, command, worker, started_at}`), why workers were skipped for a project in the last hour (`{worker, project, reason, detail}`), and how many commands this machine runs for its own central host.
- `exec.setups` (X62) → `[{copy, host, project, command}]`: this Mac's routing copies whose setup waits for the user's approval; the event `exec.setup` carries one when it starts to wait. The app asks with X60's setup modal and answers with `sync.run_setup` or `sync.skip_setup`. App only.
- `cloud.*` (X63), on the central host: `cloud.get` → the cloud workers settings of `cloud.json`, `{host_id, providers, tailscale, idle_minutes, max_machines, max_hours_month, projects, kinds}`. A provider's secret field `x` shows as `has_x: true` and the Tailscale secret as `has_client_secret`, never their values. `tailscale` is `{mode: "oauth" | "auth_key", client_id, has_client_secret, has_auth_key, tag}`. `cloud.check` → `true` once the saved OAuth client made a test key and revoked it, or an error saying why (app or paired desktop only). `kinds` lists the providers on offer with their settings fields and `billing_unit_secs`, the unit they bill every started one of (3600: by the hour). `cloud.set` takes the same keys, each optional (a provider or project set to `null` is removed; a provider's secret cannot be cleared while it has machines, so they can still be removed), and needs the app or a paired desktop: never the CLI, a phone or a worker's connection. Sessions carry `cloud: true` when made with `session.create {cloud: true}`.
- Cloud machines (X63), on the central host: `cloud.types {provider, location}` → `[{name, cores, memory_gb, arch}]`; `cloud.machines` → `{machines, removed, hours_this_month, max_hours_month, max_machines}`, each machine `{id, name, project, project_key, provider, type, location, state, since, steps: [{step, label, state, took_ms, error}], deadline, idle_until, for_session, running, error, error_since, error_at, reason, worker}` (`worker`: its id in `worker.list` once registered), with the machines removed in the last hour in `removed`; `cloud.up {project, session?}` → the machine, refused with `cloud_limit` past a limit (machine-hours count the machines still rented) and `no_listener` while the central host takes no tailnet connections, and refused while the project's `.moonlet/config.toml` cannot be read; `cloud.down {machine}` (id or name); on a machine already being removed, it tries the destroy again now (**Retry**). Event `cloud.changed`, the same as `cloud.machines`. The CLI may call `cloud.up`, `cloud.down` and `cloud.machines` (`moonlet worker up|ls|down`).
- Joining (X63): `link.join {addrs, code, name}` on a fresh cloud machine (`moonletd join <addrs> <code> --name <name>`) pairs with a join code the central host made for that machine, as device kind `cloud`, names the worker and turns heavy commands on. A join code works once, for 30 minutes, and only for the machine name it was made for; it survives a restart of the central host (kept hashed in `join-codes.json`) and stops working once its machine fails or is removed. No RPC makes one. A `cloud` device may call only `worker.register`, `worker.step`, `sync.open`, `sync.fetch`, `sync.offer`, `sync.close` and `exec.done`; it attaches to no terminal, sends no input and hears no event, and it is not listed in `mobile.status`. The worker sends `worker.step {step: "machine_setup", state, took_ms, error}` as its machine setup runs, and the central host asks it `worker.retire` before removing it.
- `job.*` (X62): every routed command is a job of its session, kept on the central host in `~/.moonlet/jobs/<session>/` (the last 50, until the session is archived). `job.list {session}` → its jobs, newest first: `{id, session, command, tool_use_id, state, started_at, ended_at, phases, timeline, worker, brought, outputs, leftovers, leftovers_folder, env, summary, output_bytes}`, `state.kind` being `waiting`, `running` (`worker`), `bringing_back`, `done` (`exit`), `stopped` (`exit`) or `lost`. `job.output {job, from}` → `{chunks: [{stream, text}], next, more}`. `job.stop {job}` and `job.stop_all {session}` stop running jobs (exit 143, with `moonlet: stopped from the Jobs panel` in the output); `job.run_here {job}` answers `not_waiting` for a job not waiting for a machine. Events: `job.changed` (the job) and `job.output {job, session, chunks}`. `moonlet exec --tool-use <id>` names the tool call a job runs for.
- `exec.*` between a central host and its workers (X62): the central host asks `exec.prepare {session}` → `{copy, state, reason}` (`state` `ready`, `making`, `setup_pending` or `failed`), fences the routing copy with `sync.update`, then `exec.start {run, copy, argv, cwd, env, tree, head, session_path, outputs}` → `true`, or `not_approved`, `busy`, `not_fenced`, `missing_tool` or `invalid_params`; the next worker is then tried, and the central host itself last. The worker sends the run's output as RunOutput frames and ends with `exec.done {run, copy, status, tree, head, pack, outputs}` → `{leftovers, folder, notes}`, after which its copy returns to the fence. `exec.cancel {run}` stops a worker's run. A routing copy (`sync.open {kind: "run"}`) lives in a repository of its own under `runs/`, syncs only at fences and never shows in `sync.list`. `heavy.approve {identity, commands, env}` (no `project`) approves a project of this machine's central host for this worker.
- `design.*` (X64): a moonlet workspace's design systems, under `~/.moonlet/design/<workspace id>/`; every call names an existing `workspace` and fails with `invalid_params` otherwise; a paired phone gets `forbidden`. `design.systems {workspace}` → `[{slug, name, sources, synced_at, synced_commit, cards, layouts, changed_sources, check_problems, to_settle, step, step_summary, steps, error}]` (a system that cannot be read lists with its `error`); `steps` is `[{step, summary}]`, every step the running sync reported, in step order, each with its last summary or `null`, and `to_settle` leaves out orphaned cards kept for now. `design.system.create {workspace, name, sources: [{project, subdir?}], cover?: "core" | "all" | "none", agent?: bool}` → `{slug, agent, agent_error}` (a `subdir` that is absolute, has `..`, is missing or links out of its project fails with `invalid_params`): the slug (a used name gets ` 2`) and, unless `agent: false`, the chat of the sync agent it starts, or why it did not start. A Design mode agent whose start fails once its chat is made (its record cannot be saved, or its first message cannot be sent) leaves no chat behind: the chat is stopped and removed, and the record forgotten. `design.system.sync {workspace, slug}` → `{agent}` asks that agent to sync again (a new chat when it has none); before the first recorded sync it asks for a build again. `design.system.remove {workspace, slug}`. `design.system.progress {workspace, slug, step, summary?}` with `step` one of `inventory`, `tokens`, `cards`, `layouts`: the steps before it stay, its summary is replaced and the steps after it are dropped. `design.system.synced {workspace, slug}` records each source's short `HEAD` (none when it cannot be read) and the time, and writes `_ds_sync.json`: both or neither. `design.check {workspace, slug, render?}` rewrites the foundation cards, `_ds_manifest.json` and `README.md`, and returns `[{path, line, kind, message}]`; with `render: true` it also has the app render every card and returns `{problems, render: {total, bad, thin, variants_identical}, render_error: null}`, after writing `.cache/render-check.json`, or, when no app renders, `{problems, render: null, render_error: "Open moonlet to render cards"}`. `design.snap {workspace, slug, path, viewport?: [w, h], variant?}` → `{path, blank}`: the app's screenshot of a card (`path` in the system), saved in its `.cache/screenshots/` under the card's own path (`components/custom/row/row--ghost-720x200.png`); `blank` under 5 KB. `design.snap` fails with `no_app` "Open moonlet to render cards" when no app renders. `design.render.ready {}`: the Mac's app (never a phone or the CLI, `forbidden`) says it renders cards; the daemon then sends it alone, on that connection, the event `design.render {id, workspace, slug, path, viewport, variant, want: "metrics" | "png"}` (`path` the card's in the system), one card at a time, and the app answers `design.render.done {id, metrics?: {flags, errors}, png_base64?, error?}` within 30 s of that card being sent. It trusts the local client as every method on the user's own socket does (the socket is `0600` and the daemon checks the peer's uid): any process of the user that reaches the socket could claim to be the app, and would then be sent the cards to render and could answer for them. No other mechanism guards it. `design.file {workspace, path}` → `{path, content_type}` of a file under the workspace's design folder, never one outside it (`..`, an absolute path or a symlink); the app reads the file itself. `design.settle {workspace, slug, card, choice: "mine" | "synced" | "remove" | "keep"}`; `keep` keeps an orphaned card for now (any other card fails), until a sync finds its sources back or the card gone, or it is removed. `design.cards {workspace, slug}` → `[{group, name, path, viewport, source, snippets, marker, problems, changed_sources, proposals, edited_by_hand, orphaned, kept}]`, each card with its check problems, its sources changed since the sync, the proposals beside it, and whether it was edited by hand, is orphaned or is kept for now. `design.detect {workspace, path}` → the folder's UI stack, such as `["React", "Tailwind"]`. Each system in `design.systems` also has `agent`, `needs_you` (`null` or `{kind: "question" | "approval", text}`) and `last_sync` (`[{path, change: "new" | "rewritten" | "removed", sources}]`). Workspace designs (X65), under `~/.moonlet/design/<workspace id>/designs/<slug>/`, each addressed as `{workspace, slug}`: `design.list {workspace}` → `[{slug, name, kind: "workspace", system, path, brief, viewport, pages: [{name, label}], updated_at, open_comments, agent, agent_state, needs_you, error}]` by name (`brief` what the user asked for; `viewport` the one it was last shown at, `WxH` in px, `1440x900` until one is saved; `pages` with `index` first, then by name; `updated_at` the newest page's change in ms, else the creation; `agent` the chat of its agent while it is still that design's, with its state and what it waits for; a design whose `design.toml` cannot be read lists with its `error`). `design.create {workspace, name, system, brief, session?, spawned_by?}` → the design as listed, with `agent_error` (why its agent did not start, or `null`): the folder made (a used name gets ` 2`) and the design's agent started, a Claude Code chat in the design's folder with its design system's folder read only. A `system` the workspace does not have fails with `invalid_params`, a `spawned_by` terminal that is not there with `invalid_params`, and `session` (session designs) with `not_yet`. With `spawned_by`, the event `design.open` follows, naming that terminal and its session. `design.remove {workspace, slug}` stops the design's agent and deletes the design. `design.viewport {workspace, slug, viewport}` saves the viewport the design was last shown at, `WxH` in px such as `390x844`, in its `design.toml`, leaving the rest of the file as it was; anything else fails with `invalid_params`. `design.comments {workspace, slug}` → the design's pins of `comments.json`, by number: `[{n, page, mid, tag, text, comment, sent_at, state}]` (`mid` the element's `data-mid`, `text` up to 60 characters of its text, `sent_at` the last time it was sent to the chat in ms or `null`, `state` `open` or `resolved`); a design without the file has none, a pin written before a field existed reads it as empty, and a file that cannot be read fails. `design.comment.put {workspace, slug, new | edit | sent}` → the pins it changed: `new: {page, mid, tag, text, comment}` pins a new comment, numbered after the highest so far (a number is never given again), on page `page` and the element `mid` (`m` and digits), with `tag` and `text` (squashed and cut to 60 characters); `edit: {n, comment}` changes pin `n`'s comment, and a changed comment is not sent any more (`sent_at` back to `null`); `sent: {pins: [{n, comment}]}` sets those pins' `sent_at` to now, each only while its comment is still `comment` (the one the chat got; a pin edited meanwhile is returned unchanged, not sent), or none of them when one is not there. A bad page, `data-mid` or tag, an empty comment or an unknown pin fails with `invalid_params`, and a `comments.json` that cannot be read is never written over. `design.comment.resolve {workspace, slug, n}` → the pin, `resolved`. `design.page {workspace, slug, page}` → `{html, version}`: a design's page, `pages/<page>.html`, as the visual editor reads it (X65 entry 9), `version` the SHA-256 of its text in hex. `design.write_page {workspace, slug, page, html, base_version, edits?}` → `{version}` replaces that page with `html` exactly as sent, when the file is still at `base_version`; `edits` says what each edit by hand the save carries did, such as `moved section m24` (none from an older app), for the summary of the snapshot taken once the design's saves stop for 10 s; a page changed on disk since, also while it is saved, fails with `stale` and is left as it is. A page name that is empty, starts with `.` or has a `/` or `\` fails with `invalid_params`. Both go through the designs folder as a handle: a design or `pages` folder swapped for a link is never followed. A save fires `design.changed` for the design, as any change of its files does. The daemon runs one change of a design's comments at a time. Each change fires `design.changed` for the design, and `design.list`'s `open_comments` counts the pins `design.comments` reads as `open`. `design.history {workspace, slug}` → the design's snapshots of `pages/` and `assets/`, newest first: `[{n, time, type: "agent_turn" | "edits_by_hand" | "restored", summary, from?, pages}]` (`n` never given again, `time` in ms, `summary` such as `Wrote git-a.html and git-b.html · 3 pages` or `Moved section m24, restyled h2 m25`, empty for a restore, whose `from: {n, time}` names the snapshot it made current; `pages` its pages, `index` first). The daemon takes one when the design's agent ends a turn (its `agent.attention` `done`) and when `design.write_page`'s saves of it stop for 10 s, each only when a file changed since the last (by SHA-256), and keeps the newest 50, in `history/<n>/` with a `snapshot.json`; each fires `design.changed` naming `history/<n>/…`. `design.snapshot.restore {workspace, slug, n}` → the `restored` entry: what is not kept yet is kept first, as `edits_by_hand`, then snapshot `n`'s files are written into `pages/` and `assets/` exactly, every other file there removed, and a `restored` snapshot recorded; an unknown `n` fails with `invalid_params`, and it fails with `busy` while the design's agent works. Every read and write goes through the designs folder as a handle and never follows a link. `design.file`'s `path` `designs/<slug>@<n>/pages/…` or `…/assets/…` is that file of snapshot `n`, as deep as the design's own, so a page's relative links resolve as they do for the design's pages (the canvas's preview). `design.open {workspace, slug}` sends every client on the Mac the event `design.open {workspace, slug, name, spawned_by?, session?}`: the app shows the design, or, with `spawned_by`, a toast. Designs stay on the Mac: a paired device hears neither `design.open` nor `design.changed`. `design.check {workspace, design, fix?}` checks a design's pages instead of a design system: `[{path, line, kind, message}]`, `kind` being `missing_mid`, `duplicate_mid` or `stylesheet` (a stylesheet linked, or imported in a `<style>`, other than `../../../systems/<system>/styles.css`; an `@import` outside a `<style>` is text, not checked); with `fix: true` the missing and repeated ids get the next free numbers first and the pages are saved. A Design mode agent's terminal (`TerminalInfo.design`) and its `agent.attention` carry `design: {kind: "sync" | "design", workspace, slug, name}`: a design system's sync agent or a design's agent. Daemons before X65 sent `design: true` for a sync agent, and a saved `true` still reads as one. Event: `design.changed {workspace, system, design, paths}`, one per changed design system or design, gathered over 150 ms, with paths relative to its folder (`system` and `design` both `null` for the workspace's other files).
- `worker.*` (X41): on the central host, `worker.register` (only from a `moonletd-worker` connection over the tailnet) and `worker.list`, each worker with `{id, name, os, arch, cores, version, projects: [{identity, path}], slots, heavy, connected_since, rtt_ms, load}`; `heavy` says it takes heavy commands. The central host sends `worker.ping` to each worker every 10 s and drops one that misses three in a row; the worker answers `{load}`, its 1-minute load average (X62). A worker registers again when its name, slots or heavy commands change. Event: `workers.changed`, the list.

## Versioning

`PROTOCOL_VERSION` is bumped on any incompatible change. When versions differ, the client shows an "upgrade daemon" action, which calls `daemon.upgrade` on an old daemon that still understands it, or restarts the daemon.
